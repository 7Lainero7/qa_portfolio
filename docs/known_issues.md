# Known Issues & Design Decisions

## ✅ RESOLVED: PATCH с `{"category": null}` вызывал 500 Internal Server Error
**История:** При передаче `null` валидатор пропускал значение, и SQLAlchemy пыталась записать `NULL` в колонку `NOT NULL`, вызывая `IntegrityError`.  
**Решение:** В `schemas.py` добавлена явная проверка: `if value is None: raise ValueError(...)`. Теперь API корректно возвращает `422 Unprocessable Entity`.

---

## 🟡 DESIGN DECISION: Нормализация пустых строк в `category`
**Описание:**  
Если при создании или обновлении расхода передать `{"category": "   "}` (только пробелы), API не возвращает `422`. Валидатор выполняет `strip()`, и если строка пуста, применяет дефолтное значение `"other"`.  

**Почему так сделано:**  
Это компромисс в пользу DX (Developer Experience). Клиент часто отправляет пустые строки вместо `null` или пропускает поле. Строгий отказ (`422`) потребовал бы от фронтенда дополнительной логики очистки данных перед отправкой.  
**Компромисс:** Мы жертвуем строгой валидацией "грязного ввода" ради устойчивости API к типичным ошибкам клиентов. В строгом финтехе это должно быть `422`, и это можно изменить, раскомментировав `raise ValueError` в `validate_update_category`.

## 🟡 DESIGN DECISION: PATCH с пустым телом `{}` возвращает 200 OK
**Описание:**  
Запрос `PATCH /api/expenses/{id}` с телом `{}` возвращает `200 OK` без изменений.  
**Почему так сделано:**  
Использование `model_dump(exclude_unset=True)` в репозитории означает "обновить только переданные поля". Если передано ничего, обновляется ничего. Возврат `400 Bad Request` здесь был бы излишне строгим и усложнил бы клиентскую логику (клиенту пришлось бы проверять объект на пустоту перед отправкой).
